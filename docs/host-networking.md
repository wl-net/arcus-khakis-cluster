# Host Networking

The compose files assume each host already provides four things that are **not** managed by this repo:

1. `br0`, the parent interface for the `arcus` macvlan network
2. `mac0`, a host-side macvlan shim holding the DC gateway address `192.168.N.1`
3. OpenVPN TAP tunnels between the three sites, with routes for the remote DC subnets
4. ufw rules that allow forwarding between the DC subnets

If any of these is missing, containers can still talk to each other within a DC, but cross-DC traffic fails: Cassandra nodes show `DN` and the ZooKeeper ensemble loses members.

> This repo is public. Never commit anything from `/etc/openvpn/pki/` (private keys, tls-crypt keys).

## Sites

| Site | DC subnet | Gateway (`mac0`) | OpenVPN |
|---|---|---|---|
| site1 | 192.168.1.0/24 | 192.168.1.1 | 2.6 |
| site2 | 192.168.2.0/24 | 192.168.2.1 | 2.7 |
| site3 | 192.168.3.0/24 | 192.168.3.1 | 2.6 |

## Tunnels

Each link is a point-to-point OpenVPN TAP tunnel. The TLS server end bridges its TAP into `br0`; the TLS client end gets an address on the server's DC subnet. TAP (not TUN) is required so the remote end shares an L2 segment with the server's containers and LAN devices.

| Link | TLS server | TLS client | Port (UDP) |
|---|---|---|---|
| site1 ↔ site2 | site1 `tap1`, bridged into `br0` | site2 `tap1`, 192.168.1.2/24 | 1197 |
| site1 ↔ site3 | site1 `tap2`, bridged into `br0` | site3 `tap1`, 192.168.1.3/24 | 1198 |
| site2 ↔ site3 | site3 `tap2`, bridged into `br0` | site2 `tap2`, 192.168.3.2/24 | 1199 |

### Layout (same on every host)

| Path | Purpose |
|---|---|
| `openvpn@siteN` | Unit for the tunnel **to peer** siteN |
| `/etc/openvpn/siteN.conf` | Config for the tunnel to siteN |
| `/etc/openvpn/pki/` | This host's cert/key, plus one tls-crypt key per link: `site1-site2-tc.key`, `site1-site3-tc.key`, `site2-site3-tc.key` |
| `/etc/openvpn/scripts/up-siteN.sh` | Up script (TLS server ends: `brctl addif br0 tapX`) |

Logs go to the journal: `journalctl -u openvpn@site2`.

### Crypto

- TLS mode with self-signed EC (prime256v1) certs, no CA. Each end pins the other with `peer-fingerprint`.
- `tls-crypt` per link, `dh none`, `data-ciphers AES-256-GCM:CHACHA20-POLY1305`. Session keys are negotiated per connection and renegotiated hourly.
- `disable-dco`: OpenVPN DCO does not support TAP.
- Static-key (`secret`) mode was removed on 2026-10-17. OpenVPN 2.7 refuses it by default and 2.8 drops it entirely, so don't reintroduce it.
- Certs are valid for 10 years (expire ~October 2036).

### Replacing a cert

On the host whose cert is being replaced:

```bash
cd /etc/openvpn/pki
S=site2   # this host's site name
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 -nodes \
  -keyout $S.key -out $S.crt -days 3650 -subj "/CN=$S"
chmod 600 $S.key
openssl x509 -in $S.crt -noout -fingerprint -sha256
```

Update `cert`/`key` in this host's configs, put the new fingerprint in `peer-fingerprint` in **both peers'** configs for this host, then restart both ends of each link. Fingerprints are not secret.

A new tls-crypt key for a link: `openvpn --genkey tls-crypt siteA-siteB-tc.key && chmod 600 siteA-siteB-tc.key`, then copy it to the other end over SSH.

## Host shim: `mac0`

A macvlan container cannot reach its parent interface's own IP. The containers' gateway (`192.168.N.1`, see the compose `ipam` config) therefore lives on `mac0`, a macvlan sibling of the containers on `br0`. The host forwards between `mac0` and the tunnels.

`mac0` is configured by systemd-networkd **only**, on all three hosts:

```ini
# /etc/systemd/network/00-mac0.netdev
[NetDev]
Name=mac0
Kind=macvlan

[MACVLAN]
Mode=bridge
```

```ini
# /etc/systemd/network/00-mac0.network  (site1 shown)
[Match]
Name=mac0

[Network]
Address=192.168.1.1/24
ConfigureWithoutCarrier=yes

[Route]
Destination=192.168.2.0/24
Gateway=192.168.1.2

[Route]
Destination=192.168.3.0/24
Gateway=192.168.1.3
```

```ini
# /etc/systemd/network/10-netplan-br0.network.d/macvlan.conf
[Network]
MACVLAN=mac0
```

networkd only creates a macvlan when the parent's `.network` file lists it. `br0`'s file is generated by netplan in `/run/systemd/network/`, so the drop-in adds it. If `br0` is ever renamed in netplan, rename the drop-in directory to match.

### Rules

- **Don't create `mac0` anywhere else** (ifupdown `/etc/network/interfaces`, networkd-dispatcher hooks, scripts). These race `br0` creation at boot, and if `mac0` already exists networkd marks `br0` `failed` (`Failed to create netdev: File exists`).
- **Any route that leaves via `mac0` must be a `[Route]` section** in `00-mac0.network`. networkd deletes routes it didn't create on links it manages whenever it restarts, including during a `systemd` package upgrade.

## Routes

| Host | Route | Source |
|---|---|---|
| site1 | 192.168.2.0/24 via 192.168.1.2 | `[Route]` in `00-mac0.network` |
| site1 | 192.168.3.0/24 via 192.168.1.3 | `[Route]` in `00-mac0.network` |
| site2 | 192.168.1.0/24 dev tap1 | kernel (address OpenVPN puts on `tap1`) |
| site2 | 192.168.3.0/24 dev tap2 | kernel (address OpenVPN puts on `tap2`) |
| site3 | 192.168.1.0/24 dev tap1 | kernel (address OpenVPN puts on `tap1`) |
| site3 | 192.168.2.0/24 via 192.168.3.2 | `[Route]` in `00-mac0.network` |

site1's up scripts also run `ip route replace` for its two routes. That's redundant now but harmless.

Other machines on a DC's LAN reach remote DCs through that DC's gateway, e.g. `192.168.2.0/24 via 192.168.1.1`.

## Firewall

Docker sets the iptables `FORWARD` policy to `DROP`. Cross-DC container traffic is forwarded by the hosts, so it's allowed by ufw routed rules, not by Docker. Every host needs:

- ufw **enabled at boot** (`ufw status`, `systemctl is-enabled ufw`)
- a routed allow for the DC subnets, e.g.
  ```bash
  ufw route allow from 192.168.0.0/22 to 192.168.0.0/22 comment 'xDC cluster traffic'
  ```
- on TLS server hosts, the OpenVPN listener ports allowed inbound (site1: 1197, 1198; site3: 1199)

## Troubleshooting

After a reboot or package upgrade, if cross-DC traffic fails, check in this order on the affected host:

```bash
systemctl is-active openvpn@siteX openvpn@siteY ufw
networkctl list | grep -E 'br0|mac0'           # both "configured", not "failed"
ip -br addr show mac0                           # 192.168.N.1/24
ip route | grep 192.168                         # matches the Routes table
bridge link | grep tap                          # TLS server ends: tap on br0
sudo ufw status verbose                         # active, routed rule present
docker exec arcus-khakis-cluster-cassandra-0-1 bash -c \
  'timeout 3 bash -c "</dev/tcp/192.168.1.10/7000" && echo OK'
```

| Symptom | Likely cause |
|---|---|
| Container gets `No route to host` to another DC | `mac0` missing; the container can't resolve its gateway (`cat /proc/net/arp` shows `00:00:00:00:00:00` for 192.168.N.1) |
| Container times out, but the host can reach the remote DC | Forwarding dropped: ufw inactive or missing routed rule (`iptables -L FORWARD -n -v` policy counter climbing) |
| Host traffic to a remote DC leaves via the default route | Cross-DC route deleted (`ip route get 192.168.2.1`); it isn't a `[Route]` section |
| `networkctl` shows `br0` `failed` | Something other than networkd created `mac0` |
| Tunnel down for ~2 min after the peer restarts | Expected: the client reconnects on `keepalive 10 120` ping-restart |
